# Route Timing And Point Visits

Документ фиксирует новую логику обходов для версии 0.3.0 после уточнения ТЗ: норматив маршрута должен рассчитываться автоматически по истории, а каждая контрольная точка должна подтверждаться двумя NFC-сканами.

## Цели

- Не задавать норматив маршрута вручную, а вычислять его по фактическим обходам.
- Выявлять отклонения: не выполнен обход, отхождение от графика, слишком быстро, слишком долго, подозрительно.
- Уведомлять Проверяющего по триггерам.
- Усложнить имитацию обхода простым быстрым сканированием меток.
- Дать Проверяющему понятную картину по магазину: история обходов, ответственные лица, триггеры, отчеты, фотоотчеты, учетные данные и штат.

## Новая модель точки

Старая модель считала точку пройденной после одного NFC-скана. Новая модель:

1. СК приходит к точке и сканирует NFC.
2. Backend фиксирует `arrive`.
3. Точка блокируется на минимальное время, по умолчанию 90 секунд.
4. Пока точка заблокирована, повторный скан этой же точки не засчитывает уход.
5. После истечения блокировки СК повторно сканирует эту же NFC-метку.
6. Backend фиксирует `depart`.
7. Только после `depart` точка считается завершенной, и система ожидает следующую точку маршрута.

Блокировка должна быть настройкой backend:

- `pointDwellSeconds` - базовое значение, по умолчанию `90`;
- допустимый диапазон для настройки ТЗ: 60-120 секунд.

## Состояния точки в обходе

- `pending` - точка еще не начата;
- `arrived` - первый скан есть, идет обязательное ожидание;
- `ready_to_depart` - минимальное время прошло, ожидается повторный скан этой же метки;
- `completed` - второй скан принят, точка закрыта.

## Данные backend

Минимальные новые сущности:

### patrol_point_visits

Фиксирует посещение точки в рамках конкретного обхода.

Поля:

- `id`;
- `patrol_id`;
- `route_id`;
- `patrol_point_id`;
- `sort_order`;
- `arrived_at`;
- `departed_at`;
- `locked_until`;
- `dwell_seconds`;
- `arrival_event_id`;
- `departure_event_id`;
- `status`;
- `created_at`;
- `updated_at`.

### patrol_events

Текущую таблицу NFC-событий нужно расширить:

- `scan_action`: `arrive` или `depart`;
- `point_visit_id`;
- `accepted`: принято ли событие в прогресс обхода;
- `rejection_reason`: причина отказа, если событие сохранено как технический факт, но не меняет прогресс.

### route_timing_profiles

Хранит рассчитанный норматив маршрута.

Поля:

- `id`;
- `route_id`;
- `shop_id`;
- `sample_count`;
- `average_total_seconds`;
- `suspicious_fast_seconds`;
- `fast_seconds`;
- `slow_seconds`;
- `calculated_from`;
- `calculated_to`;
- `created_at`;
- `updated_at`.

## Расчет норматива маршрута

Норматив маршрута считается по завершенным обходам за последние 14 дней.

В выборку входят:

- обходы со статусом `completed`;
- обходы конкретного `routeId`;
- обходы, где все точки имеют `arrive` и `depart`;
- обходы без `missed_point`;
- обходы, которые не были отменены и не были завершены вручную без полного маршрута.

Из выборки исключаются:

- `cancelled`;
- `overdue`, если он не был затем завершен полным маршрутом;
- обходы с неполной лентой точек;
- обходы с техническими дублями, которые нельзя однозначно интерпретировать;
- обходы с уже зафиксированным критическим нарушением маршрута.

Базовый расчет:

```text
average_total_seconds = average(completed_at - started_at)
```

Если выборка меньше минимального порога, профиль считается недостаточно надежным:

- `sample_count < 5` - норматив не применяется автоматически, показывается статус `insufficient_data`;
- `sample_count >= 5` - норматив активен.

Пороговые значения для версии 0.3.0:

- `fast_seconds = average_total_seconds * 0.70`;
- `slow_seconds = average_total_seconds * 1.30`;
- `suspicious_fast_seconds = average_total_seconds * 0.50`.

Эти коэффициенты должны быть конфигурируемыми. После накопления данных их можно заменить на percentile-based расчет.

## Триггеры

### Не выполнен обход

Срабатывает, когда плановый обход не начат или не завершен в допустимое окно расписания.

Инцидент:

- `patrol_overdue`;
- severity: `critical`.

### Отхождение от графика

Срабатывает, когда обход стартовал слишком рано или слишком поздно относительно расписания и `earlyStartMinutes`.

Инцидент:

- `schedule_deviation`;
- severity: `warning` или `critical` по величине отклонения.

### Слишком быстро

Срабатывает, когда общее время маршрута меньше `fast_seconds`.

Инцидент:

- `route_too_fast`;
- severity: `warning`.

### Подозрительно быстро

Срабатывает, когда общее время маршрута меньше `suspicious_fast_seconds` или когда точки закрываются с минимальным dwell почти без переходов между ними.

Инцидент:

- `route_suspiciously_fast`;
- severity: `critical`.

### Слишком долго

Срабатывает, когда общее время маршрута больше `slow_seconds`.

Инцидент:

- `route_too_slow`;
- severity: `warning`.

### Слишком короткое пребывание на точке

Срабатывает, если departure-скан пришел раньше `locked_until`.

Инцидент:

- `point_dwell_too_short`;
- severity: `warning`.

В таком случае точка не закрывается, backend возвращает состояние ожидания до `lockedUntil`.

## Уведомления Проверяющему

Все триггеры создают инцидент и вызывают общий механизм push-уведомления.

Получатели:

- пользователи с ролью `inspector`, назначенные на магазин;
- при необходимости `admin`.

Payload push должен содержать:

- `type`;
- `shopId`;
- `routeId`;
- `patrolId`;
- `incidentId`;
- `severity`.

## Представление Проверяющего

Проверяющий должен видеть по назначенным магазинам:

- историю выполненных обходов;
- ответственных лиц на магазинах;
- список триггеров и инцидентов;
- карточку магазина;
- все виды операционных отчетов;
- фотоотчеты;
- контрольные точки и фото точек;
- штат магазина;
- маршруты, графики и текущие нормативы.

В версии 0.3.0 backend отдает эти данные через существующие и будущие control endpoints. Главная точка расширения:

```http
GET /api/v1/control/shops/:shopId/overview
```

Предлагаемый состав ответа:

```json
{
  "shop": {},
  "staff": [],
  "routes": [],
  "timingProfiles": [],
  "recentPatrols": [],
  "incidents": [],
  "reports": [],
  "photoReports": []
}
```

## Последствия для mobile

Mobile больше не считает точку пройденной после первого скана.

Экран обхода должен:

- получить `nfc-wait-state`;
- показать ожидаемую точку;
- при первом скане отправить `arrive`;
- показать таймер блокировки 60-120 секунд;
- после разблокировки ждать повторный скан той же метки;
- отправить `depart`;
- только после успешного `depart` перейти к следующей точке.
