# Модуль Patrol Routes

Модуль `patrol-routes` управляет несколькими маршрутами одного магазина. Маршрут хранит категорию `internal` или `external` и отдельный порядок контрольных точек.

## Эндпоинты

- `POST /api/v1/patrol-routes` — создать маршрут из точек магазина; роли `admin`, `route_setter`, `local_route_setter`.
- `GET /api/v1/patrol-routes/shop/:shopId` — список маршрутов магазина; роли `admin`, `route_setter`, `local_route_setter`, `inspector`.
- `GET /api/v1/patrol-routes/:id` — карточка маршрута с точками; роли `admin`, `route_setter`, `local_route_setter`, `inspector`.
- `GET /api/v1/patrol-routes/:id/versions` — история версий, от новой к старой; те же роли и ограничения магазинов, что у карточки.
- `PATCH /api/v1/patrol-routes/:id` — изменить название, категорию, активность или состав точек; роли `admin`, `route_setter`, `local_route_setter`.
- `DELETE /api/v1/patrol-routes/:id` — мягко удалить маршрут через `deleted_at`; роли `admin`, `route_setter`, `local_route_setter`.

## Правила

- Все точки маршрута должны принадлежать тому же магазину, что и маршрут.
- Порядок маршрута хранится в `patrol_route_points.sort_order`, отдельно от `patrol_points.sort_order`.
- Расписание может быть привязано к маршруту через `routeId`.
- Обход может быть запущен с `routeId`; backend считает количество точек по маршруту и отклоняет NFC-событие для точки вне маршрута.
- `PATCH isActive` включает или отключает маршрут без удаления. Отключённые маршруты остаются в рабочем списке и могут быть включены повторно.
- `DELETE` устанавливает `isActive=false` и `deleted_at`, после чего маршрут скрывается из обычных списков. Снимки и история завершённых обходов сохраняются.
- Отключить или удалить маршрут, используемый активным расписанием, нельзя: сначала необходимо отключить связанное расписание. Backend возвращает `PATROL_ROUTE_IN_ACTIVE_SCHEDULE`.
- Для каждой точки маршрута можно задать `dwellSeconds` от `0` до `120`; значение по умолчанию — `90`.
- Настройка хранится в связи `patrol_route_points`, поэтому одна контрольная точка может иметь разные выдержки в разных маршрутах.
- Для временного пожароопасного режима настройщик создаёт отдельный маршрут и расписание, затем активирует нужный набор и деактивирует обычный без удаления истории.
- `local_route_setter` может читать и изменять маршруты только назначенных ему магазинов; `route_setter` и `admin` работают со всеми магазинами.

## Настройка выдержки

Порядок маршрута по-прежнему задаётся через `patrolPointIds`. Необязательный `pointSettings` содержит индивидуальные выдержки:

```json
{
  "shopId": "00000000-0000-4000-8000-000000000001",
  "name": "Fire-risk external route",
  "category": "external",
  "patrolPointIds": [
    "00000000-0000-4000-8000-000000000101",
    "00000000-0000-4000-8000-000000000102"
  ],
  "pointSettings": [
    {
      "patrolPointId": "00000000-0000-4000-8000-000000000101",
      "dwellSeconds": 0
    },
    {
      "patrolPointId": "00000000-0000-4000-8000-000000000102",
      "dwellSeconds": 120
    }
  ]
}
```

`pointSettings` может содержать только точки из `patrolPointIds`. При изменении состава маршрута существующие точки сохраняют свои выдержки, новые неуказанные точки получают значение `90`; при `PATCH` без замены состава можно передать только изменяемые настройки.

## История версий и снимок обхода

Миграция `1781782000000` добавляет `patrol_route_versions` и `patrols.route_snapshot`.
Создание и каждый успешный PATCH маршрута сохраняют новую неизменяемую версию в одной
транзакции с названием, категорией, активностью, составом точек, маршрутным порядком и выдержками.
Мягкое удаление и восстановление через общий `/archive/patrol-routes/:id` также сохраняют версии.
Параллельные изменения сериализуются блокировкой строки маршрута; при ошибке откатываются
метаданные, связи и версия вместе. Сохранение выдержек при перестановке выполняется под этой блокировкой.

Ответ истории имеет общий тип `PatrolRouteVersion[]`: `id`, `routeId`, `version`, `createdAt` (UTC),
`actorId`, `actorFullName`, `authorizationId`, `snapshot`. Для универсального настройщика сохраняются
введённое ФИО и ID авторизации. `snapshot` содержит `name`, `category`, `isActive` и массив
`points: [{ patrolPointId, sortOrder, dwellSeconds }]`.

Для существующих маршрутов миграция записывает начальную версию текущего состояния с пустым
автором. Более ранние изменения не восстанавливаются задним числом.

При старте обхода backend сохраняет отдельный снимок активных точек (`PatrolSnapshotPoint[]`)
и рассчитывает `totalPoints` из него. Захват снимка блокирует параллельное редактирование маршрута.
Последующие изменения маршрута не меняют состав, порядок и выдержки уже начатого обхода.
Снимок доступен в поле `routeSnapshot` ответа старта/карточки обхода и через mobile route endpoint.
В shared-интерфейсе `PatrolRoute.points[]` поле `dwellSeconds` обязательно.

## Проверка транзакций на PostgreSQL

`apps/backend/src/database/route-snapshots.integration.spec.ts` проверяет миграции, откат
создания точки вместе с NFC, конфликт UID, неизменность снимка, порядок событий,
историю автора и параллельные правки маршрута. Для запуска задайте `PATROL_TEST_DATABASE_URL`
на отдельную тестовую PostgreSQL БД и выполните:

```powershell
npm exec -w @patrol/backend -- jest --runInBand route-snapshots.integration.spec.ts
```

Тест применяет миграции и добавляет собственные записи, не очищает БД. Без переменной
окружения этот интеграционный набор пропускается; обычные unit/API-тесты работают без PostgreSQL.
