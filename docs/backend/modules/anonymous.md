# Anonymous Appeals

Модуль `anonymous` закрывает backend-часть раздела СК "Анонимно" для версии 0.3.0.

## Назначение

Anonymous appeal - бизнес-анонимное обращение сотрудника СК по выбранному магазину. В рабочем представлении проверяющего и администратора обращение не раскрывает автора. Сущность хранит магазин, категорию, статус, текст и технический контекст приема.

Технический audit при этом не отключается: backend фиксирует факт отправки защищенного запроса, но не пишет текст обращения в `audit_log.meta.body`.

## Endpoints

- `POST /api/v1/mobile/anonymous` - создать обращение, роль `security_guard`;
- `GET /api/v1/anonymous` - список обращений, роли `admin`, `inspector`;
- `GET /api/v1/anonymous/:id` - карточка обращения, роли `admin`, `inspector`;
- `PATCH /api/v1/anonymous/:id` - сменить статус, роли `admin`, `inspector`.

Для `inspector` список и карточка ограничиваются назначенными магазинами.

## Категории

- `message`;
- `complaint`;
- `safety`;
- `other`.

## Статусы

- `new`;
- `in_review`;
- `resolved`;
- `archived`.

## Создание

```json
{
  "shopId": "00000000-0000-4000-8000-000000000001",
  "category": "message",
  "message": "Сообщение для службы контроля"
}
```

СК может создать обращение только по назначенному магазину. Backend проверяет область доступа по `shopId` из JWT.

## Audit

Для `POST /api/v1/mobile/anonymous` глобальный audit interceptor маскирует body:

```json
{
  "anonymousAppeal": true,
  "shopId": "00000000-0000-4000-8000-000000000001"
}
```

Текст обращения, категория и другие поля body в audit log не сохраняются.

## Ограничения Версии 0.3.0

- Файлы к anonymous appeal не прикрепляются.
- Нет отдельного процесса назначения ответственного.
- Нет выгрузки anonymous appeals.
- Business-представление не раскрывает автора, но технический audit сохраняет факт защищенного запроса.
