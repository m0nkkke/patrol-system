# Seed-данные backend 0.3.0

В проекте есть два идемпотентных seed-скрипта. Перед запуском необходимо применить все миграции.

## Быстрая ручная проверка

Команда:

```powershell
npm run backend:seed:manual
```

Скрипт создает один магазин, внутренний маршрут из трех точек, утреннее расписание с ранним стартом, завершенный обход и активный обход. События обходов соответствуют контракту 0.3.0: для каждой пройденной точки существуют `arrive`, `depart` и запись `patrol_point_visits`.

Активный обход уже находится у первой точки в состоянии `ready_to_depart`. В JSON-результате seed команда выводит объект `nextAction` с `patrolId`, UID метки и ожидаемым `scanAction = depart`.

Учетные записи:

| Назначение | Логин | Ключ |
|---|---|---|
| Администратор | `seed.admin` | `SADM-SEED-0001` |
| СК | `seed.employee` | `EMPL-SEED-0001` |
| Проверяющий | `seed.manager` | `MNGR-SEED-0001` |
| Универсальный настройщик | `seed.route-setter` | `RSET-SEED-0001` |

Универсальный настройщик входит через `POST /api/v1/auth/universal-route-setter/login` и при каждом входе передает ФИО исполнителя. Остальные учетные записи используют `POST /api/v1/auth/login`.

NFC UID:

- `04a1b2c3d4e501`
- `04a1b2c3d4e502`
- `04a1b2c3d4e503`

Рекомендуемый endpoint сканирования:

```http
POST /api/v1/mobile/patrols/:patrolId/point-visits/scan
```

Сначала отправляется `scanAction = arrive`, после завершения блокировки той же метки отправляется `scanAction = depart`. Старый endpoint `/events` оставлен как совместимый alias, но для нового мобильного клиента использовать его как основной не следует.

## Полный сценарный набор

Команда:

```powershell
npm run backend:seed:scenarios
```

Сценарный seed предназначен для проверки мобильного приложения, панели проверяющего, отчетности и управленческих витрин. Он создает:

- четыре магазина с маршрутами в состояниях `ready`, `setup_in_progress` и `not_configured`;
- внутренний и внешний маршруты одного магазина;
- расписания `morning`, `noon`, `evening` с окнами раннего старта;
- все роли 0.3.0: СК, настройщик, локальный настройщик, проверяющий и администратор;
- универсальную учетную запись настройщика;
- СК с доступом к нескольким магазинам и неактивную учетную запись;
- шесть завершенных обходов за последние 14 дней для расчета норматива маршрута;
- профиль маршрута со средним нормативом 20 минут и порогами быстрого/медленного прохождения;
- обходы во всех состояниях, включая два активных NFC-сценария: блокировка и готовность к убытию;
- все девять типов триггеров и инцидентов версии 0.3.0;
- все шесть типов операционных отчетов и все статусы отчета;
- демонстрационную WebP-фотографию, прикрепленную к `photo_report` через записи `file_assets` и `patrol_report_files`.

Основные учетные записи:

| Назначение | Логин | Ключ |
|---|---|---|
| Администратор | `demo.admin` | `ADMN-DEMO-0001` |
| СК, Иркутск | `demo.employee.irkutsk` | `EMPL-IRKK-0001` |
| СК, Москва | `demo.employee.moscow` | `EMPL-MSKK-0001` |
| СК, несколько магазинов | `demo.employee.multi` | `EMPL-MULT-0001` |
| Неактивный СК | `demo.employee.inactive` | `EMPL-INAC-0001` |
| Проверяющий, Иркутск | `demo.manager.irkutsk` | `MNGR-IRKK-0001` |
| Проверяющий, Москва | `demo.manager.moscow` | `MNGR-MSKK-0001` |
| Локальный настройщик | `demo.local-route-setter` | `LRST-DEMO-0001` |
| Универсальный настройщик | `demo.route-setter` | `RSET-DEMO-0001` |

После выполнения команда печатает JSON с ключами доступа, ID магазинов, ключевых обходов, отчетов, анонимных обращений, архивной точки, маршрута с нормативом и NFC UID. Это позволяет запускать ручные запросы без поиска UUID в базе.

## Порядок запуска

При использовании локального PostgreSQL:

```powershell
$env:DATABASE_HOST='127.0.0.1'
$env:DATABASE_PORT='5432'
$env:DATABASE_USER='patrol'
$env:DATABASE_PASSWORD='patrol'
$env:DATABASE_NAME='patrol'
$env:DATABASE_SSL='false'

npm run backend:migration:run
npm run backend:seed:manual
# или
npm run backend:seed:scenarios
```

Оба скрипта можно запускать повторно. Они обновляют стабильные seed-сущности и перестраивают NFC-события/посещения точек, не создавая копии пользователей, магазинов, маршрутов и обходов.

Seed предназначен только для development и тестовых окружений. На production выполнять его нельзя.

## Покрытие сценарного seed

`npm run backend:seed:scenarios` формирует репрезентативный набор данных 0.3.0:

- все состояния обхода: `pending`, `in_progress`, `completed`, `overdue`, `cancelled`;
- оба состояния ожидания повторного NFC-сканирования: заблокированная точка и `ready_to_depart`;
- индивидуальные выдержки точек маршрута, включая граничные значения `0` и `120` секунд;
- завершенные `arrive`/`depart` посещения, поздно синхронизированное событие и событие деактивированной после сканирования точки;
- все типы инцидентов: `short_interval`, `long_interval`, `missed_point`, `patrol_overdue`, `point_dwell_too_short`, `route_suspiciously_fast`, `route_too_fast`, `route_too_slow`, `schedule_deviation`;
- все шесть типов операционных отчетов и статусы `draft`, `submitted`, `cancelled`;
- локальный WebP-файл фотоотчета;
- активные и неактивные пользователи, назначения в один и несколько магазинов;
- готовый, настраиваемый и ненастроенный магазины, внутренний и внешний маршруты;
- архивную контрольную точку для проверки списка архива и восстановления;
- анонимные обращения категорий `message`, `complaint`, `safety`, `other` в статусах `new`, `in_review`, `resolved`, `archived`.

Сценарный seed идемпотентен: повторный запуск обновляет сущности с маркером `scenarios-seed-v030`, а не создает их копии. В итоговом JSON печатаются ID ключевых обходов, отчетов, архивной точки и анонимных обращений.
