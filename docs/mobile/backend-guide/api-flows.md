# API-потоки приложения

## 1. Обычный вход

1. Получить или создать стабильный `deviceId`.
2. Вызвать `POST /api/v1/auth/login`.
3. Сохранить `accessToken` и `refreshToken`.
4. Вызвать `GET /api/v1/mobile/me`.
5. Построить UI по роли и capabilities.
6. Зарегистрировать push token, если разрешения получены.

## 2. Вход универсального Настройщика

1. Показать отдельный экран входа Настройщика.
2. Запросить ключ доступа и ФИО реального исполнителя.
3. Вызвать `POST /api/v1/auth/universal-route-setter/login`.
4. Сохранить токены, `authorizationId` и `authorizationFullName`.
5. Вызвать `GET /api/v1/mobile/me`.
6. Открыть сценарий настройки маршрутов.

Обычный `/auth/login` для универсальной учетной записи вернет ошибку.

## 3. Выбор магазина СК

1. После `GET /mobile/me`, если роль `security_guard`, вызвать `GET /api/v1/mobile/shops`.
2. Показать список разрешенных магазинов.
3. Сохранить выбранный `shopId` как текущий контекст.
4. Все последующие экраны обхода, графика, отчетов и anonymous строить относительно выбранного магазина.

## 4. План и локальные напоминания

Backend отдает расписания с `period` и `earlyStartMinutes`. Mobile должен заранее загрузить план и поставить локальные уведомления, работающие без сети.

Основной endpoint:

```http
GET /api/v1/mobile/shops/:shopId/patrol-schedules/available
```

Если доступен endpoint плана локальных напоминаний, использовать его как источник для локального календаря уведомлений. После синхронизации с backend пересоздавать локальные уведомления.

## 5. Старт обхода

```http
POST /api/v1/mobile/patrols/start
```

Body:

```json
{
  "shopId": "00000000-0000-4000-8000-000000000001",
  "scheduleId": "00000000-0000-4000-8000-000000000002",
  "routeId": "00000000-0000-4000-8000-000000000003"
}
```

После старта приложение сразу переходит в режим ожидания NFC. В новой логике точка закрывается только после двух сканов: `arrive` и `depart`.

## 6. Автоматическое ожидание NFC

После старта или восстановления активного обхода:

```http
GET /api/v1/mobile/patrols/:id/nfc-wait-state
```

Или для текущего активного обхода:

```http
GET /api/v1/mobile/patrols/active/nfc-wait-state
```

Если `mode = waiting_for_nfc` или `mode = waiting_for_departure`, экран обхода должен сам включить foreground NFC listening. Отдельная кнопка "сканировать" по ТЗ 0.3.0 не нужна.

При чтении метки отправить событие в `scanContract.endpoint`:

```json
{
  "patrolPointId": "<expectedPoint.id>",
  "nfcUid": "04a1b2c3d4e5f6",
  "scannedAt": "2026-08-19T05:00:00.000Z",
  "deviceId": "android-device-01",
  "scanAction": "<expectedScanAction>",
  "lat": 56.010563,
  "lng": 92.852572,
  "gpsAccuracy": 5
}
```

Если `expectedScanAction = arrive`, backend фиксирует приход к точке и возвращает `lockedUntil`. Mobile показывает таймер блокировки 60-120 секунд и не дает завершить точку до разблокировки.

Если `expectedScanAction = depart`, mobile должен ждать повторный скан той же NFC-метки. Только после успешного `depart` точка считается пройденной, и приложение снова запрашивает wait-state для следующей точки.

После каждого успешного скана снова запросить wait-state.

## 6.1. Нормативы маршрута и триггеры

Backend будет автоматически рассчитывать норматив маршрута по завершенным обходам за последние 14 дней. Mobile не должен вычислять норматив самостоятельно.

Mobile должен только:

- отображать текущий статус обхода;
- показывать уведомления и ошибки backend;
- не скрывать от пользователя, что обход ушел в просрочку;
- открывать экран истории/деталей по push payload, если роль пользователя это поддерживает.

Триггеры backend:

- обход не выполнен;
- отхождение от графика;
- маршрут пройден слишком быстро;
- маршрут пройден подозрительно быстро;
- маршрут пройден слишком долго;
- точка покинута раньше минимального времени.

## 7. Попытка пропуска точки

Если пользователь приложил метку другой будущей точки, mobile не должен локально засчитывать точку. Нужно отправить:

```http
POST /api/v1/mobile/patrols/:id/missed-point-attempts
```

Body:

```json
{
  "expectedPatrolPointId": "<expectedPoint.id>",
  "attemptedPatrolPointId": "<scannedPoint.id>",
  "nfcUid": "04a1b2c3d4e5f6",
  "scannedAt": "2026-08-19T05:00:00.000Z",
  "deviceId": "android-device-01"
}
```

## 8. Offline sync NFC

Каждое NFC-событие сначала сохраняется локально с `localId`. При сети отправляется пачкой:

```http
POST /api/v1/mobile/patrols/:id/events/sync
```

Пачка максимум 200 событий. Статусы `created`, `duplicate`, `late_sync`, `point_deactivated` считаются принятыми backend и не требуют повторной отправки.

## 9. Операционные отчеты СК

Backend поддерживает шесть типов:

- `photo_report`;
- `morning`;
- `closing`;
- `sunday`;
- `heating`;
- `evacuation`.

Поток:

1. Создать черновик `POST /api/v1/mobile/reports`.
2. Прикрепить фото `POST /api/v1/mobile/reports/:id/files`.
3. Отправить отчет `POST /api/v1/mobile/reports/:id/submit`.
4. При необходимости отменить черновик `POST /api/v1/mobile/reports/:id/cancel`.

Формы отчетов могут отличаться по набору `fields`. До финального уточнения ТЗ формы лучше строить конфигурируемо, а не зашивать жестко в экран.

## 10. Anonymous

СК может отправить бизнес-анонимное обращение:

```http
POST /api/v1/mobile/anonymous
```

Body:

```json
{
  "shopId": "00000000-0000-4000-8000-000000000001",
  "category": "message",
  "message": "Сообщение для службы контроля"
}
```

Категории:

- `message`;
- `complaint`;
- `safety`;
- `other`.

В рабочем представлении backend не раскрывает автора. Mobile тоже не должен показывать обращение как персональное.

## 11. Refresh и обработка 401

При `401`:

1. Один раз вызвать `/auth/refresh`.
2. Если refresh успешен, повторить исходный запрос.
3. Если refresh тоже вернул `401`, очистить токены и открыть экран входа.
