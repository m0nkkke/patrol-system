# Эксплуатация production

## Рабочий контур

Production mobile зависит от постоянно доступного Patrol System API и внешних сервисов доставки.

```text
Android-приложение
        │
        ├── HTTPS ── reverse proxy ── NestJS backend
        │                                  ├── PostgreSQL
        │                                  ├── Redis
        │                                  └── файловое хранилище
        │
        ├── EAS Update ── совместимые OTA bundle
        ├── Expo Push ─── шлюз push
        └── Firebase ──── FCM и Crashlytics
```

Подробное развёртывание сервера находится в
[`docs/deployment/backend-production.md`](../../deployment/backend-production.md). Mobile-команда
контролирует клиентский URL и совместимость, но не хранит серверные секреты в EAS.

## Требования к backend

Production API работает круглосуточно по стабильному HTTPS-домену. Reverse proxy завершает TLS и
передаёт запросы NestJS. PostgreSQL и Redis используют постоянные volumes, а фотографии —
резервируемое файловое или объектное хранилище.

Health endpoint применяется внешним мониторингом. Доступность проверяется из публичной сети, а не
только с сервера. Сертификат и DNS обновляются до истечения срока и изменения инфраструктуры.

Backend запускается с production-конфигурацией, сильными уникальными секретами и закрытым Swagger.
Демонстрационные seed-данные в рабочий контур не загружаются. Миграции выполняются контролируемо до
переключения новой версии приложения backend.

## Требования к mobile delivery

Production EAS environment содержит стабильный `EXPO_PUBLIC_API_BASE_URL` и Firebase file
configuration. Production channel используется только для проверенных обновлений. Android
keystore и Google Play credentials принадлежат организации, принимающей продукт.

Релиз формируется из зафиксированного Git commit. Перед сборкой рабочее дерево не содержит
случайных изменений, сгенерированных native-каталогов, `.env` или credentials. Зависимости
воспроизводятся из общего lock-файла.

Новый AAB сначала проходит Google Play Internal Testing. Устанавливается именно store build, после
чего выполняются вход, загрузка профиля, навигация, один изменяющий запрос, получение защищённого
файла, регистрация push-токена и проверка обновлений. После успешной проверки артефакт переводится
на следующий track без пересборки из другого commit.

## Совместимость mobile и backend

Backend разворачивается с сохранением контрактов, необходимых уже установленным клиентам. При
поэтапной миграции сначала добавляются новые поля и endpoint, затем выпускается клиент, и только
после обновления активной базы удаляется устаревшее поведение.

Новые необязательные поля допустимы. Удаление обязательных полей, смена enum, формата времени,
семантики статусов или правил авторизации требует согласованного плана доставки.

При изменении публичного адреса старый домен продолжает обслуживать клиентов до распространения
новой сборки или OTA. Редиректы API используются осторожно: Authorization, multipart-запросы и
методы мутаций должны сохраняться корректно.

## Push-уведомления

В backend включается отправка push и проверяется исходящий доступ к Expo Push Service. Expo project
имеет действующий FCM V1 credential, связанный с тем же Firebase-проектом, что и
`google-services.json` внутри приложения.

Ошибки доставки контролируются по ответам Expo и состоянию токенов в backend. Недействительный
токен деактивируется. Массовая проблема с FCM не должна блокировать обходы и отчёты; пользователи
сохраняют доступ к данным через приложение.

## OTA-обновления

Production OTA публикуется после проверки того же изменения в preview. Совместимость определяется
runtime version. Обновление не используется для изменения native dependency или permission.

Публикация фиксируется сообщением, commit и ответственным за выпуск. После доставки контролируются
Crashlytics и доступность API. При росте ошибок rollout останавливается или возвращается последний
проверенный bundle.

## Наблюдаемость

Состояние mobile оценивается по нескольким источникам:

- Firebase Crashlytics — native crash, ANR и важные JS errors;
- серверные логи — ошибки API и доменные отказы;
- health monitoring — доступность backend и зависимостей;
- статистика push delivery — недействительные токены и ошибки FCM;
- пользовательские обращения — проблемы конкретных устройств и разрешений;
- EAS dashboard — состояние build и update deliveries.

Диагностика начинается с определения версии установленной сборки, runtime, channel, роли,
устройства, времени и endpoint. Чувствительные данные не запрашиваются у пользователя и не
публикуются в задачах сопровождения.

## Данные и резервирование

Серверная база и файловое хранилище резервируются по регламенту backend. SQLite телефона не
считается резервной копией. Неотправленные события существуют только на устройстве до
синхронизации; удаление приложения уничтожает их.

Перед принудительной переустановкой у сотрудника контроля проверяется отсутствие pending-событий.
При длительной недоступности API сначала восстанавливается backend, затем клиентам предоставляется
время для синхронизации.

## Реакция на сбои

При недоступности API активный обход продолжает поддерживаемую офлайн-часть, но новые входы,
запуски и итоговое завершение недоступны. После восстановления сервисов синхронизация запускается
автоматически.

При ошибке мобильного JavaScript используется OTA-исправление или откат. При native crash,
несовместимости Firebase, проблеме разрешений или подписи выпускается новая сборка.

При компрометации access key пользователя ключ заменяется на backend, что отзывает связанные
сессии. При компрометации FCM service account или Android upload key выполняется процедура
ротации соответствующего сервиса; секрет не заменяется изменением mobile `.env`.

## Завершение эксплуатации

Перед сменой владельца или подрядчика передаются организационные доступы, документация,
репозитории, EAS project, Firebase project, Google Play application, signing materials и правила
резервного восстановления. Порядок передачи описан в
[документе о доступах](access-handover.md).
