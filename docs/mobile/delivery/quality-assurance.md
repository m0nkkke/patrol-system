# Контроль качества мобильного приложения

## Уровни проверки

Качество mobile подтверждается сочетанием статических проверок, unit-тестов, интеграционной
проверки с backend и испытаний на физическом Android-устройстве. Ни один отдельный уровень не
заменяет остальные: Node-тесты не воспроизводят NFC и разрешения, а ручная проверка не гарантирует
типовую целостность всех чистых функций.

## Автоматические проверки

Из корня монорепозитория выполняются:

```powershell
npm run test -w @patrol/mobile
npm run typecheck -w @patrol/mobile
npm run lint -w @patrol/mobile
```

Unit-тесты расположены рядом с чистыми модулями в файлах `*.test.ts`. Они проверяют форматирование
и валидацию ключа, маршрутизацию по ролям, подготовку данных карточек, фильтры, расписания и
локальную проекцию двухфазного обхода.

Изменения общих DTO дополнительно проверяются сборкой `@patrol/shared` и typecheck backend. Перед
релизом используется зафиксированный lock-файл; самопроизвольное обновление зависимостей не
совмещается с функциональным исправлением.

## Интеграционная среда

Preview-проверка выполняется с публичным тестовым backend, отдельными PostgreSQL, Redis и файловым
хранилищем. Тестовые данные включают все роли, магазины с разными состояниями настройки, активные и
исторические обходы, нарушения, отчёты и обращения.

Испытания выполняются на том же API URL и EAS channel, которые встроены в передаваемый preview
APK. Проверка только development build не подтверждает работу OTA, release-mode Firebase и
поведение автономного приложения без Metro.

## Ролевое покрытие

Для администратора проверяются управление магазинами и пользователями, контрольные данные,
история, нарушения, отчёты, обращения и доступ к NFC-операциям.

Для проверяющего проверяется ограничение назначенными магазинами, списки сотрудников, сводки,
обходы, расследования, отчёты и обращения. Попытка прямого перехода за пределы области должна быть
отклонена backend.

Для универсального настройщика проверяется второй шаг входа с ФИО, выбор магазина и отражение
исполнителя в аудите. Для локального настройщика проверяется невозможность работы с чужим
магазином.

Для сотрудника контроля проверяются один и несколько назначенных магазинов, план, запуск обхода,
отчёт и анонимное обращение. При смене магазина данные предыдущего контекста не должны оставаться
на экране.

Все ролевые представления проверяются с пустыми данными, длинными списками, серверным поиском,
пагинацией, обновлением, ошибкой сети, системной кнопкой Back и прямой навигацией из push.

## Физические испытания

NFC проверяется реальными метками, зарегистрированными в тестовом backend. Используются корректная
текущая метка, метка следующей точки, неизвестная метка, выключенный NFC и устройство без
поддержки технологии.

Двухфазный сценарий подтверждает отдельные `arrive` и `depart`, запрет раннего ухода, граничную
выдержку, переход к следующей точке и завершение последней. Закрытие и повторный запуск приложения
во время таймера не должны сбрасывать состояние.

Камера и галерея проверяются с разрешением и отказом, допустимым изображением, слишком большим
файлом и повторной загрузкой после ошибки. Защищённое изображение не должно открываться без
авторизации.

Геолокация проверяется с точным и неточным результатом, отключённым датчиком, отказом разрешения и
работой в помещении. Отсутствие координат не блокирует NFC-событие согласно текущей продуктовой
модели.

Push проверяется в foreground, background и после полного закрытия приложения. Нажатие должно
открыть разрешённый объект, а отозванная сессия — экран входа. Crashlytics подтверждается на
release-mode сборке и не должен содержать чувствительные payload.

## Офлайн и смена пользователя

Активный обход открывается онлайн, затем сеть отключается. Пользователь выполняет обе фазы точек,
перезапускает приложение и продолжает по восстановленному состоянию. После возвращения сети
события отправляются один раз и в исходном порядке.

Отдельно воспроизводится разделение владельцев: пользователь A создаёт offline event и выходит,
пользователь B входит и работает со своей областью, затем A возвращается и синхронизирует свою
очередь. Интерфейс, счётчики и запросы B не должны включать записи A.

Проверяются отказ backend в середине пакета, повторная отправка после восстановления, поздняя
синхронизация, деактивация точки после фактического скана и удаление приложения при наличии
pending events как документированный риск потери локальной очереди.

## Релизная проверка

Preview APK устанавливается как новый пакет и как обновление предыдущей сборки. Проверяются
первый запуск, разрешения, вход, защищённые файлы, push token и работа после перезагрузки телефона.

Совместимое JavaScript-изменение публикуется в preview channel и подтверждается после перезапуска
приложения. Native-изменение проверяется только новой сборкой. Финальный AAB проходит Google Play
Internal Testing до перевода на production track.

Результат испытания фиксирует артефакт EAS или Google Play, commit, устройство и Android OS,
backend environment, выполненный сценарий и наблюдаемый результат. Дефект содержит минимальные
шаги воспроизведения и безопасные фрагменты Metro, backend logs, `adb logcat` или Crashlytics.
