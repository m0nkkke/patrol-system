# Авторизация и безопасность

## Модель входа

Приложение использует персональный ключ доступа. Перед отправкой ключ нормализуется: приводится к
верхнему регистру, очищается от недопустимых символов и форматируется группами. Сам ключ не
сохраняется после успешного входа.

В запрос входа передаётся стабильный `deviceId`. Он генерируется при первом запуске и хранится в
SecureStore. Идентификатор позволяет backend различать сессии одного пользователя на разных
устройствах и адресно отзывать refresh-сессию.

Обычный процесс входа:

1. Клиент отправляет ключ и `deviceId` в endpoint авторизации.
2. Backend возвращает access- и refresh-токены.
3. Клиент сохраняет токены в SecureStore и в памяти auth store.
4. Клиент загружает `/mobile/me`.
5. Профиль, capabilities и назначения формируют ролевой интерфейс.

## Универсальный настройщик

Общая учётная запись универсального настройщика требует идентификации конкретного исполнителя.
Первичный запрос входа возвращает доменный код `AUTH_ACTOR_FULL_NAME_REQUIRED`. Только этот код, а
не префикс ключа или текст ошибки, включает второй шаг.

Пользователь вводит ФИО, после чего клиент вызывает специальный endpoint с исходным ключом,
`deviceId` и ФИО. Backend создаёт отдельный контекст авторизации и возвращает его в токенах и
профиле. ФИО хранится в памяти экрана до завершения входа и не передаётся через route params.

## Хранение токенов

Access- и refresh-токены хранятся через Expo SecureStore. Они не помещаются в AsyncStorage,
SQLite, параметры маршрутов или логи. В памяти токены доступны только auth store и HTTP-клиенту.

Access-токен добавляется к защищённым запросам как Bearer token. Refresh-токен используется только
endpoint обновления и выхода.

## Тихое обновление сессии

При ответе `401` HTTP interceptor выполняет одну попытку обновить токены и повторяет исходный
запрос. Параллельные ошибки авторизации объединяются одним refresh-запросом. Маркер повторной
попытки исключает бесконечный цикл.

Если обновление не удалось, клиент очищает локальную сессию. Сетевой сбой сам по себе не считается
подтверждённым отзывом пользователя и не должен приводить к потере доступного офлайн-состояния.

## Проверка актуальности сессии

После входа приложение периодически запрашивает профиль и повторяет проверку при возвращении из
фона. Backend валидирует активность пользователя и версию его сессий. Деактивация пользователя,
смена ключа доступа или административный отзыв сессий приводят к отказу следующего защищённого
запроса и локальному выходу.

Проверка также обновляет роль, назначения и capabilities. Поэтому изменение полномочий начинает
действовать без переустановки приложения.

## Холодный запуск без сети

После успешного получения профиля клиент сохраняет в SQLite снимок без токенов. Если при следующем
запуске токены существуют, но сеть недоступна, разрешено восстановить недавно подтверждённый
профиль. Снимок ограничен по времени и применяется только при сетевой ошибке.

Ответы `401`, `403` и другие подтверждённые ответы backend никогда не маскируются локальным
снимком. После появления сети heartbeat или обычный API-запрос повторно подтверждает сессию.

## Выбор магазина и область данных

Сохранённый магазин сотрудника контроля сверяется с актуальным списком назначений. При одном
магазине он выбирается автоматически, при нескольких требуется пользовательский выбор. Для других
ролей рабочий магазин берётся из профиля либо выбирается внутри разрешённого сценария.

Query cache очищается при выходе, а связанные запросы инвалидируются при смене магазина. Backend
самостоятельно проверяет назначение магазина в каждом чувствительном endpoint.

## Выход

При явном выходе клиент пытается отозвать refresh-сессию на backend, затем независимо от результата:

- удаляет токены и выбранный магазин из SecureStore;
- удаляет снимок профиля;
- удаляет runtime-снимки текущего пользователя;
- очищает Query Client;
- очищает пользовательский контекст Crashlytics;
- возвращает экран входа.

Накопленные события обхода не передаются другому пользователю. Они остаются в локальных таблицах
со своим `user_id` и могут быть синхронизированы только после повторного входа владельца.

## Журналирование и конфиденциальность

В диагностические события запрещено включать:

- ключи доступа;
- access- и refresh-токены;
- заголовок Authorization;
- ФИО и текст анонимного обращения;
- NFC UID;
- точные координаты;
- содержимое загружаемых файлов.

Разрешены технические сведения, необходимые для диагностики: источник ошибки, тип операции, роль,
идентификатор пользователя, канал сборки и информация о среде выполнения. Серверный audit остаётся
каноническим журналом изменяющих операций.
