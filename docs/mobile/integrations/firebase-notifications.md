# Firebase, уведомления и диагностика

## Компоненты интеграции

В мобильном приложении используются:

- Expo Notifications для разрешений, Android-канала, Expo Push Token и локальных уведомлений;
- Expo Push Service как серверный шлюз доставки;
- Firebase Cloud Messaging для доставки push на Android;
- Firebase Crashlytics для native crash и важных JS-ошибок;
- Expo Constants для связи токена с EAS project ID.

Firebase не хранит бизнес-данные Patrol System и не заменяет backend.

## Доставка server push

Путь сообщения:

```text
Patrol System backend
        ↓
Expo Push Service
        ↓
Firebase Cloud Messaging
        ↓
Android-устройство
```

После успешного входа приложение:

1. создаёт Android notification channel;
2. проверяет, что запущено на физическом устройстве;
3. запрашивает системное разрешение;
4. получает Expo Push Token с EAS project ID;
5. отправляет токен, `deviceId`, платформу и версию приложения backend.

Отказ пользователя или ошибка регистрации push не блокируют остальные функции. Backend хранит
токены устройств и деактивирует недействительные токены по результату доставки.

При открытом приложении обработчик показывает баннер, добавляет уведомление в системный список и
воспроизводит звук. Нажатие на уведомление может открыть карточку нарушения или обхода согласно
payload и роли пользователя. Такой переход проходит обычную проверку авторизации и доступа.

## События backend

Backend определяет получателей и отправляет push для поддерживаемых бизнес-событий, включая
нарушения, просрочки и отмену обхода. Сбой внешнего push-сервиса не должен откатывать основную
операцию: событие обхода или нарушение сохраняются независимо от доставки уведомления.

Для отправки production push в окружении backend включается:

```env
PUSH_NOTIFICATIONS_ENABLED=true
```

`EXPO_PUSH_ACCESS_TOKEN` требуется только тогда, когда для проекта Expo включена дополнительная
защита Push Service access-токеном.

## Локальные напоминания

Локальные напоминания не проходят через backend в момент показа. Клиент периодически получает
план обходов, где время уже рассчитано backend с учётом часового пояса магазина, сохраняет
occurrence в SQLite и планирует системное уведомление на `notificationAt`.

Если ранний старт разрешён, первое уведомление срабатывает в `notificationAt`. Следующие
напоминания планируются на `plannedStartAt` и через 10, 20 и 30 минут после него. Время в момент
или после `dueAt` не используется. Когда сотрудник успешно начинает этот обход, оставшиеся
уведомления occurrence-а отменяются и помечаются локально, чтобы обновление плана не создало их
повторно.

При обновлении плана приложение сохраняет неизменившиеся уведомления, отменяет устаревшие и
создаёт новые. План актуализируется после входа, при длительной работе приложения и после успешной
синхронизации обхода. При выходе или входе под ролью без обходов локальный план очищается.

Нажатие на напоминание выбирает назначенный магазин и открывает экран обхода. Если назначение уже
отозвано, последующая серверная проверка запрещает действие.

## Firebase Android configuration

Android application в Firebase должен иметь тот же package name, что и приложение. Клиентская
конфигурация загружается из Firebase Console как `google-services.json`.

Для локального prebuild файл находится по пути:

```text
apps/mobile/google-services.json
```

Для EAS Build он создаётся как file environment variable:

```text
GOOGLE_SERVICES_JSON
```

`app.config.js` использует путь из этой переменной на EAS builder и локальный файл на машине
разработчика. Репозиторий и EAS upload исключают Firebase-файлы, поэтому конфигурация должна быть
загружена в каждое EAS environment, где выполняется сборка.

## FCM V1 credentials

Приложению недостаточно одного `google-services.json`. Для отправки Android push через Expo в
разделе Credentials существующего EAS-проекта должен быть привязан Google Service Account Key for
FCM V1 из того же Firebase-проекта.

Service account содержит закрытый ключ. Он хранится только в защищённом хранилище владельца и в
EAS Credentials, не добавляется в репозиторий и не передаётся как `EXPO_PUBLIC_` переменная.

Sender ID в Firebase-конфигурации приложения и FCM credential должен относиться к одному проекту.
Несоответствие приводит к ошибкам регистрации или доставки.

## Crashlytics

React Native Firebase инициализируется при старте нативного приложения. Общий logger:

- задаёт технические метаданные сборки;
- связывает события с внутренним идентификатором и ролью пользователя;
- отправляет неожиданные render errors;
- фиксирует значимые ответы API и программные ошибки;
- пишет подробности в консоль development-среды.

Ожидаемые validation errors и обычные пользовательские отказы не отправляются как сбои. Debug
сбор Crashlytics отключён конфигурацией проекта; проверка реальной доставки выполняется на
preview или production build.

Native crash обычно отправляется после следующего запуска приложения. Non-fatal JS error
появляется в Firebase Console после обработки сервисом.

## Конфиденциальность диагностики

Crashlytics не должен получать ключи доступа, токены, ФИО, NFC UID, точные координаты, содержимое
обращений и фотографии. Контекст ошибки формируется из заранее разрешённых технических полей, а не
из полного Axios request или произвольного состояния экрана.

Доступ к Firebase Console выдаётся только сотрудникам, которым необходимы диагностика и
сопровождение. При передаче проекта владелец организации предоставляет доступ через роли Firebase,
а не передаёт личную учётную запись.

## Проверка интеграции

Корректность push подтверждается появлением Expo Push Token на backend и доставкой события на
реальное устройство в закрытом и открытом состояниях приложения. Дополнительно проверяется
навигация из payload и поведение после отзыва сессии.

Crashlytics проверяется контролируемой ошибкой, проходящей через общий logger, и подтверждением
события в Firebase Console. Искусственный crash не должен оставаться доступным конечному
пользователю в production-интерфейсе.
