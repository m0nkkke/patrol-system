# Взаимодействие с backend

## Назначение интеграции

Мобильное приложение является клиентом Patrol System API. Backend выполняет авторизацию,
проверяет роли и назначения, хранит бизнес-данные и принимает окончательные решения по обходам.
Клиент не подключается напрямую к PostgreSQL, Redis или файловому хранилищу.

Каноническое описание серверных модулей находится в [`docs/backend`](../../backend/README.md), а
актуальная машиночитаемая схема endpoint формируется Swagger при запуске backend. Этот документ
фиксирует только правила, обязательные для мобильного клиента.

## Базовый адрес

Адрес API задаётся при формировании JavaScript bundle:

```env
EXPO_PUBLIC_API_BASE_URL=https://patrol.example.ru/api/v1
```

Переменная обязательна, не содержит секрет и доступна пользователю установленного приложения.
Production-сборка должна использовать стабильный HTTPS-домен. Локальные адреса и временные
туннели допустимы только в development или изолированном preview-окружении.

Клиент удаляет один завершающий слеш, поэтому endpoint формируются одинаково для значений с ним и
без него. Переключение окружения выполняется сборкой или совместимым OTA-обновлением, а не ручным
выбором сервера пользователем.

## Авторизация запросов

Защищённые запросы содержат:

```http
Authorization: Bearer <access-token>
```

Стабильный `deviceId` передаётся в операциях авторизации, регистрации push-токена и других
mobile-сценариях, где его предусматривает DTO. Анонимное обращение также может использовать
`x-device-id` как технический заголовок.

Access-токен обновляется централизованно. Feature-код не должен самостоятельно читать SecureStore,
добавлять Authorization или повторять refresh-логику.

## Группы API

Mobile использует несколько областей API:

| Область | Назначение |
|---|---|
| `/auth` | Вход, вход универсального настройщика, refresh и logout |
| `/mobile` | Профиль, магазины сотрудника, обход, расписание, отчёты и push token |
| `/control` | Безопасные представления проверяющего и администратора |
| `/shops`, `/users` | Административное управление |
| `/patrol-points`, `/patrol-routes`, `/patrol-schedules` | Настройка точек, маршрутов и расписаний |
| `/anonymous` | Контроль и обработка обращений |
| `/files` | Авторизованная выдача изображений |

Полный перечень методов и DTO не копируется в mobile-документацию, чтобы серверная реализация,
Swagger и общие типы не расходились.

## Контракты типов

Общие DTO и enum находятся в `packages/shared`. Mobile импортирует их как типы, когда runtime
значение не требуется. Локальные типы допускаются для UI-проекций и ответов, специфичных для
клиентского представления, но не должны переопределять значения серверных enum строками в разных
частях приложения.

Изменение серверного контракта считается совместимым, если установленный клиент продолжает
получать обязательные поля ожидаемого типа и прежнее значение enum сохраняет смысл. Удаление поля,
изменение семантики, обязательности или значения enum требует согласованного выпуска backend и
mobile.

## Ошибки

Backend возвращает HTTP-статус, доменный `code`, сообщение и допустимые дополнительные сведения.
Клиент принимает решения по `code`, а не по тексту сообщения. Текст может изменяться и
локализоваться без изменения контракта.

Обработка разделяется по категориям:

- validation и domain errors показываются в контексте формы или действия;
- `401` инициирует одну попытку refresh;
- подтверждённый повторный `401` завершает локальную сессию;
- `403` означает отсутствие полномочий и не должен обходиться клиентом;
- `404` для точечной карточки отображает отсутствие или недоступность объекта;
- `408`, `429` и `5xx` считаются временными либо операционными ошибками;
- отсутствие ответа классифицируется как сетевая ошибка и позволяет использовать предусмотренный
  локальный fallback.

Неизвестный доменный код должен отображаться безопасным общим сообщением и попадать в диагностику
без тела чувствительного запроса.

## Идемпотентность и повторы

Офлайн-события получают UUID на устройстве. Тот же `localId` используется при каждой повторной
отправке. Backend хранит уникальность идентификатора и возвращает уже созданное событие без дубля.

Автоматический повтор допустим для:

- refresh-защищённого исходного запроса после успешного обновления токена;
- синхронизации событий с постоянным `localId`;
- чтения данных;
- явно идемпотентных серверных операций.

Создание пользователя, магазина, маршрута, черновика отчёта или другая неидемпотентная мутация не
должна повторяться скрыто без подтверждённого контрактом ключа идемпотентности.

## Согласование состояния

После успешной мутации клиент инвалидирует связанные query key и получает актуальное состояние с
backend. Для активного обхода server wait-state остаётся базой, а локальная очередь применяется как
временная проекция до синхронизации.

При конфликте локального и серверного состояния приоритет имеет подтверждённый ответ backend.
Исключение составляет ещё не отправленный факт физического NFC-скана: он сохраняется до получения
конечного результата синхронизации.

## Доступность и безопасность

Production API должен быть доступен по HTTPS с валидным публичным сертификатом. Адрес должен
стабильно разрешаться из мобильных сетей и не зависеть от VPN разработчика, домашнего компьютера
или временного туннеля.

В клиент не включаются:

- JWT-секреты backend;
- пароль базы данных или Redis;
- Firebase service account;
- ключ подписи Android;
- учётные данные Google Play;
- административные сервисные токены.

Все значения с префиксом `EXPO_PUBLIC_` считаются открытыми.
